# S-3 · ABS-Login, Play-Session und Streaming gegen Lorenz' Server

- **Getestet:** 30.10.2026, Quest 2, Horizon OS 2.9, Commits 23b2323/9ce750e
- **Server:** ABS 2.37.1, HTTPS-Domain im Heimnetz (Adresse bewusst nicht dokumentiert)
- **Ergebnis:** ✅ Erfolgskriterium erfüllt: Ein Multi-Track-Buch streamt, der Sync kommt im ABS-Web-UI an.

## Beobachtungen
- Anmelden über HTTPS klappt (JWT mit `x-return-tokens`).
- Ein Buch mit mehreren Audiodateien startet, die Anzahl der Tracks wird korrekt angezeigt.
- Springen, Stoppen und Sync funktionieren.
- **HTTP ist gesperrt** (Android blockiert Cleartext). Laut §3.2 muss HTTP im LAN funktionieren.

## Entscheidungen
- Ziel-ABS-Version: **2.37.1**, identisch mit dem lokalen Testserver (§13 Punkt 9).
- HTTP: **Opt-in pro Server in der App** (§3.2 Rev. 3, #4). `network_security_config` erlaubt
  Cleartext auf Plattformebene, die App setzt die Zustimmung selbst durch.

## Erkenntnisse aus der Entwicklung (lokaler Testserver)
- `/auth/refresh` rotiert Access- **und** Refresh-Token. Ein bereits benutzter Refresh-Token wurde
  vom Testserver kurz danach noch einmal akzeptiert. Darauf verlässt sich die App nicht.
- Alte Access-Tokens bleiben bis zum Ablauf gültig (JWT, kein Widerruf).
- Streams (`/api/items/{id}/file/{ino}`) verlangen den Bearer-Header (ohne → 401) und
  unterstützen Range-Requests (206).
- Opus ohne `audio/ogg` in `supportedMimeTypes` → `playMethod` 2, HLS unter `/hls/{session}/output.m3u8`.
- `sync` und `close` antworten mit Klartext `OK`, nicht mit JSON.
